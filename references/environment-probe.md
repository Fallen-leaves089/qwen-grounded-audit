# 环境与能力探测

## 原则

- 只记录当前会话实际探测到的事实，不沿用上一次会话或默认环境的假设。
- 先做只读探测，再做需要副作用或联网的动作。
- 不预置平台避坑清单；环境差异通过探测、证据和记忆处理。
- 工具缺失、权限不足或输出不可解析时，标记未覆盖，不模拟结果。

## 必记字段

| 字段 | 说明 |
|---|---|
| 工作目录 | 实际检查根目录，不用相对路径猜 |
| 操作系统家族与版本 | 用于解释命令和运行时差异 |
| 架构 | 处理器架构和运行时架构分开记录 |
| shell 与版本 | 实际执行命令的 shell |
| 解释器 | Python、Node、Java 等的实际路径和版本 |
| Git | 版本、仓库根、当前分支、工作区状态 |
| 构建工具 | 实际可用的构建、测试、包管理工具及版本 |
| 容器/虚拟化 | 运行时是否可用、实际架构、权限 |
| 网络 | 是否可联网、是否被代理或策略限制 |
| 写权限 | 当前目录、临时目录、报告目录是否可写 |
| 宿主工具 | 文件、搜索、命令、子代理、网页、提问等能力 |
| 权限模式 | 当前会话的审批和沙箱边界 |

## 能力状态

每个能力标记为：

- `native`：宿主原生提供，可直接使用；
- `partial`：可用但有限制，例如输出截断、只读、仅部分目录；
- `absent`：不存在或被策略禁止；
- `unknown`：尚未探测，不能当成可用。

`unknown` 不是 `native`。`partial` 和 `absent` 都要在报告中转成未覆盖项。

## 探测顺序

1. 读取当前目录、宿主和权限元数据；
2. 查询工具是否存在及版本；
3. 查询只读状态（仓库状态、目录清单、服务监听、配置）；
4. 需要时再执行带副作用的测试、构建或联网；
5. 记录命令、退出码、关键输出和执行目录。

不要把“命令帮助能打开”当成“功能已验证”；只验证了帮助或枚举能力时，明确写“仅验证工具可用”。

## 缺失能力

- 没有命令执行：只能做静态阅读，测试/构建/迁移标未覆盖。
- 没有网络：不能查在线依赖公告或外部文档，标未覆盖。
- 没有写权限：报告和记忆改为待写入，不能在别处偷偷落盘。
- 没有子代理：两轴顺序执行，不假装并行。
- 没有交互提问：选择最保守范围，在报告开头写明假设。

## 记录纪律

- 报告中写清实际 shell、解释器和执行目录，不要只写“已运行”。
- 新发现的可复用失败机制，核实后写入本地记忆；不要把它直接升级成所有项目的通用规则。
- 单项目普通 bug 留在报告里，不写入跨项目记忆。
- 不记录个人绝对路径、密钥、客户数据或目标原文。
